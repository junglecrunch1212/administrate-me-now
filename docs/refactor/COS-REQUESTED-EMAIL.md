# Requested CoS email

MODERNIZE: a current authenticated private iMessage, dashboard or Gmail request
can ask CoS to email that requester now. Confirmation chooses only an enabled CoS
Gmail sender and the requesting member's current allowed address; multiple choices
require a destination choice. The original source, exact subject/body and selected
account remain in the private v5 response receipt. Pinned `llm-task` evidence does
not grant permission: independent OpenClaw and domain policies each check the
source-bound action, current authority and expiry before the existing sender runs.
The existing final allowlist, governance, rate limit, content/privacy guard,
provider permit and attempt/result ledger remain in force. No new OAuth or sender
is introduced, and legacy approvals retain their existing path.

Grounding skill 1.1.2 retains the natural reminder-title and scoped-negative
rules from 1.0.3 alongside the closed email rule. A reminder to email supplies no
send authority; a no-send restriction denies sending. A no-reminder restriction
does not deny an affirmative send-now request. Exact quotes, sender, recipient,
content, current source and independent approval bindings remain unchanged.

Use `administrateme_confirm_requested_email`, then the existing
`administrateme_cos_response` with the returned `approval_event_id`. Read
`administrateme_requested_email_status` after a timeout or from another private
conversation of the same member. Only an exact terminal `sent` with its original
approval/host/outbound chain proves a send. Unknown contact remains unknown across
restart and cannot automatically retry. A Gmail-origin new email does not borrow
its inbound RFC thread; ordinary final replies retain that separate existing route.

Focused acceptance composes all three real intake paths, encrypted history,
independent policy receipt consumption and the actual Gmail adapter with synthetic
provider/model clients. The pinned native hook test checks the real current-input
and policy runner, later veto, source/expiry mismatch and closed per-tool rules.
These are isolated proofs, not live household provider writes. Future scheduled
email, outside contacts, attachments and arbitrary retrieved-content disclosure
are subsequent outcomes; an immediate email confirmation is not a timer.

Recovery after any v5 response history stays on this schema-aware release:

```bash
python -m bootstrap.request_actions --instance-dir "$ADMINME_INSTANCE_DIR" disable
python -m bootstrap.request_actions --instance-dir "$ADMINME_INSTANCE_DIR" status
```

Use the deployed interpreter and actual instance directory. This revokes new
request-policy execution without changing grants or deleting history; ordinary
acquisition and legacy routes remain available. Verify normal readiness and the
existing sources; a pending new email must fail before provider contact. Re-enable
preserves the cutoff, so old pending requests do not resume. Before new history,
a pre-switch updater failure may restore the known-working predecessor. Do not
roll an older schema registry back over new v5 response history.
